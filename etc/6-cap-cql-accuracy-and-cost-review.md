# Review: cap-cql Accuracy and Costs

The skill is compact and intentionally targets `@cap.core/ql`, not the CDS compiler parser. The biggest improvements concern avoiding overbroad scope claims and unnecessary data—not shortening the reference.

## Validation

Reviewed `skills/cap-cql/SKILL.md` against local CAP 10.3.0, `@cap.core/ql` 2.2.6, the HCQL adapter implementation, and an in-memory SQLite database. These checks establish behavior for the tested implementations, not every CAP version, runtime, or database.

The CDS compiler parser was used for comparison, not as the skill's intended target. Differences from that parser are not defects in this skill. The skill also intentionally presents a restricted feature set rather than every capability of `@cap.core/ql`.

No skill files were changed as part of this review. Line references below refer to the reviewed snapshot.

## Accuracy

### 1. Resolved: Remove the Overbroad Scope Statement

**Location:** lines 8–17.

The skill intentionally focuses on `@cap.core/ql`, not the CDS compiler parser. Its statement that it covers CQL “across query interfaces” does not make that parser scope clear.

Record-style INSERT/UPDATE and to-one shorthand behaved differently through the two parsers. These differences support naming the intended parser; they do not justify changing the examples to compiler syntax.

The deliberately restricted feature set is an authoring decision, not an accuracy finding. Do not expand the skill to reveal excluded capabilities.

**Resolution:** removed the broad “across query interfaces” statement from line 8 without adding parser details or revealing excluded capabilities.

### 2. Resolved: Cross-Reference for Filter Scope

**Location:** lines 49–53; the grouped example at lines 80–94 has the same issue.

The current example returned both Drama and non-Drama books for a matching author. It also retained an author with no books, because `!=` is null-safe. This behavior is consistent with the documented semantics, not an accuracy defect:

```sql
SELECT from Authors {
  ID, books { title }
} where books.genre.name != 'Drama'
```

The subsequent **Concise semi-joins** section already demonstrates filtered `EXISTS` together with an infix-filtered expand, explicitly distinguishing narrowing authors from narrowing books. No additional example or rewrite is needed.

**Resolution:** added a short cross-reference from Deep Reads to Concise semi-joins without duplicating the examples.

### 3. Resolved: Distinguish Missing-Row Behavior by Operation

**Location:** line 115.

The original text incorrectly stated that all to-one queries raise a not-found error when the row is missing. For the intended query interface, `SELECT` returns `null`; only `UPDATE` and `DELETE` raise not-found errors.

**Resolution:** updated To-one queries to distinguish `SELECT` from `UPDATE` and `DELETE`.

### 4. Resolved: Integer Keys Can Be Generated by Custom Handlers

**Location:** lines 135–149.

The deep INSERT omits parent and child keys, while the read examples use integer keys. This is valid when custom handlers generate integer keys, as they do in bookshop. The skill's UUID rule describes automatic UUID generation; it does not exclude custom key generation.

**Resolution:** withdrawn as an accuracy finding. No additional IDs or UUID-only assumption are needed in the example.

## Costs

### 5. Resolved: Prefer Explicit Projections in the Examples

**Location:** lines 33, 49, 72, and 109.

Repeated `*` encourages fetching unnecessary columns. Nested `{*}` can multiply that payload across many children.

**Resolution:** retained the flattened-read wildcard example to demonstrate override semantics; replaced the other explicit wildcards and the implicit wildcard in the basic semi-join example with small projections. Added one concise “minimize payloads” instruction, without adding lines to the examples. To-one queries examples remain abbreviated to focus on addressing syntax.

### 6. Resolved: Native JSON Expands Use One Database Roundtrip

**Location:** line 20.

The intended database implementations optimize expands using database-native JSON functions, reducing database roundtrips to one. The skill's pushdown guidance is therefore appropriate; the earlier roundtrip caveat was not useful for this target.

Large results still incur database, serialization, and transfer costs, but the payload instruction added for finding 5 and the existing LIMIT examples already address those concerns without another qualification.

**Resolution:** withdrawn as a requested skill change. Retain the pushdown guidance without adding the proposed roundtrip caveat.
